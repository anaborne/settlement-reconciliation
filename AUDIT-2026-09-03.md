# Audit, 2026-09-03

This file records an audit of the README in this repository, carried out on 2026-09-03 against
a build of the models from the committed fixture in `fixtures/`. Eleven defects were found over
two rounds, and every figure below was re-derived from `settlement_reconciliation.duckdb` after
a clean rebuild at commit 37630e5.

## What was found

Every defect was in the prose. The SQL and the Python were read in full in both rounds and
nothing was found wrong in either: the join grain, the reason-code precedence, the severity
mapping, the match-rate denominator, the open-run handling, the epoch conversions, and the two
singular tests that run the reconciliation backwards all hold.

## Issue by issue

### 1. Series evidence

The README read: "Within the run that produced 8 of the 11, unsettled and settled rows share the
series `KXATPCHALLENGERMATCH`, `KXITFWMATCH`, and `KXCS2GAME`." The run that produced 8 of the
11 is run 7. Inside run 7, `KXITFWMATCH` is 1 row and settled, and `KXCS2GAME` is 1 row and
settled, so neither carries an unsettled row there. The sentence had merged run 7 with run 9.
The bullet now states the settled share of each of the five series that carry an unexplained
row, measured across the whole extract, and reports the one series inside run 7 that carries
both. All six figures reproduce: `KXITFMATCH` 33 of 37, `KXT20MATCH` 8 of 12,
`KXATPCHALLENGERMATCH` 16 of 18, `KXCS2GAME` 16 of 17, `KXITFWMATCH` 17 of 18, and inside run 7
`KXATPCHALLENGERMATCH` at 6 settled and 2 unsettled.

### 2. Decisions per run

The opening sentence read "281 decisions across 12 collection runs". `stg_runs` holds 12 runs
and `count(distinct run_id)` over `stg_decisions` is 5. The per-run counts are run 1 at 1, run 7
at 18, run 9 at 2, run 11 at 89, and run 12 at 171. Seven runs produced nothing. The opening now
reads "281 decisions from 5 of the 12 collection runs in the run log", and the note about
`ruleset-4` now records that six other runs are also empty.

### 3. Scope of the inert-control claim

"One control is inert and the harness proves it" was written next to a 15-row table, which read
as a statement about the whole suite. Three generic tests outside the harness are also true by
construction. The `accepted_range` on `match_rate` compares a filtered count to `count(*)` over
the same group. The `unique` on `decision_date` is guaranteed by the `group by` that builds the
daily fact. The `not_null` on `is_settled` reads `settlements.ticker is not null`. The section
now names the inert control as a sixteenth case and states the three separately.

### 4. Ruleset values in the daily table

The Rulesets column printed `1, 2, 3, 5` and `5`. `rulesets_active` is a `string_agg` over the
values the extract writes, so the model returns `ruleset-1, ruleset-2, ruleset-3, ruleset-5` for
2026-08-24 and `ruleset-5` for the other five dates. The six cells now carry what the model
returns.

### 5. Where freshness is declared

The README credited `stg_settlements` with the `loaded_at_field` and the freshness thresholds.
`stg_settlements.sql` is a plain select with no configuration. The block sits on the source
table at `models/staging/_sources.yml:15-18`, and `dbt source freshness` names the node
`forward_test.settlements`. The sentence now names the source.

### 6. Property file names

The README said generic tests are declared in "the `schema.yml` beside each model". No file of
that name exists. The 77 generic tests are declared in `_intermediate.yml` (13), `_marts.yml`
(27), and `_staging.yml` (37), and `_sources.yml` declares none. The sentence now names the
three files.

### 7. Harness runtime

The README gave "about a minute" in two places. The harness makes 16 project copies and runs dbt
up to twice per case with partial parsing off. Measured runs came in at 3m22s, 4m10s, 4m30s and
close to 6m on different machines. Round 1 replaced the figure with a range of three to six
minutes, which no single measurement supports as an upper bound. Both places now read "a few
minutes".

### 8. Fixture size

The README gave 44 KB in two places, which is what `du` reports after rounding each of the five
files up to a 4 KB block. The files total 31,037 bytes. Both places now read 31 KB.

### R2-1. Contract documentation

The round-1 text read "All three are kept as contract documentation and none of them can catch a
regression." Two of the three sit on `fct_daily_reconciliation`, which does set
`contract: {enforced: true}`. The third sits on `int_decision_settlement`, which has no contract
block at all. The sentence now reads "All three are kept because they state the intended shape
of the output, and none of them can be made to fail by any change to the data."

### R2-2. Inert-control wording

The round-1 line opened "One of the 15 controls the harness examines is inert" and closed on a
construction the rest of the README avoids. It now reads "A sixteenth control is inert, and the
harness demonstrates it." The harness runs 15 fault injections and one unfalsifiable case, so 16
controls are examined and the inert one is the sixteenth.

### R2-3. Harness sentence shape

The round-1 line ran three clauses together and carried the unmeasured range from issue 7. It is
now two sentences: "It runs as its own CI job on every push and exits non-zero if any control
sleeps through its fault. A full pass takes a few minutes."

One thing could not be corrected. The subject line of commit ee05bea says "Five of the twelve
runs produced no decision" when five runs produced all 281 and seven produced none. The commit
body and the README are correct. Amending the subject would require a force push and was left
alone.

## What was checked and found correct

The reproduce path in the README runs as written. `uv venv --python 3.12`, `uv pip install -r
pyproject.toml`, `DBT_PROFILES_DIR=. DBT_DATA_DIR=fixtures dbt build`, `dbt docs generate
--static`, `dbt source freshness`, `sqlfluff lint models tests snapshots`, and
`scripts/verify_controls.py` all behave as documented.

- `dbt build` finishes at PASS=90 WARN=1 ERROR=0 SKIP=0 TOTAL=91 and exits 0. The single warning
  is `assert_no_unexplained_breaks` reporting 11 results, which is the documented backlog.
- Every headline count reproduces from the committed fixture. `stg_decisions` holds 281 rows,
  `stg_settlements` 263, `stg_runs` 12, and `stg_unscoreable` 1. 263 of the 281 decisions settle,
  a match rate of 0.9359430604982206. The 18 that do not split into 11 `unexplained` at severity
  `high`, 6 `settlement_pending` at `info`, and 1 `unscoreable_market` at `low`.
- All six rows of `fct_daily_reconciliation` reproduce, including the 0.7250 on 2026-08-24 and
  the 0.8889 on 2026-08-29, the runs and rulesets columns, and all six net settled figures.
- The settlement window figures reproduce. The watermark is 2026-08-29 20:53:54 UTC, the
  close-to-load lag runs from 87 s to 72828 s over 263 rows, the unexplained rows sit 380406 s
  to 418206 s before the window opens, the 6 pending rows sit 366 s to 7566 s past the watermark,
  and the unscoreable row sits 63294 s inside the window.
- The confounded correlation holds. All 11 unexplained rows fall in the first 21 decisions by
  `decided_at`, between 2026-08-24 02:38 and 13:00 UTC, under rulesets 1 through 3. The other 260
  decisions ran under `ruleset-5` and carry 0 unexplained rows.
- `target/manifest.json` carries 82 data tests, 77 generic and 5 singular. The five singular
  tests are the ones the README names.
- `scripts/verify_controls.py` exits 0 and reports 15 of 15 injected faults caught by the control
  that names them, with the sixteenth case reported as inert. The run took 4m30s.
- `assert_decisions_inside_run_window` returns 0 rows across all 281 decisions, and run 11 keeps
  its 89 decisions with a null `finished_at`.
- Ordering run 7's 18 decisions by event time gives the interleave the README claims, so no load
  boundary separates its settled rows from its unsettled ones.
- `scripts/extract.py` names 5 tables and 31 columns.
- `sqlfluff lint` exits 0 with no violations. `dbt source freshness` reports `ERROR STALE` on
  `forward_test.settlements`. `dbt docs generate --static` writes `target/static_index.html`,
  which is the file CI copies to Pages, and the published page returns 200.
- The fee-change simulation starts from the row the README names. The lowest `change_id` in the
  fixture is `000d1db5-db74-426b-9637-3ed46fd59a67` at `fee_multiplier` 1.0 and `scheduled_at`
  2026-08-24 22:40:00, which the script moves to 1.25 and 2026-08-25 04:40:00.

## What remains unverifiable

Everything that needs the private `forward_test.sqlite` is outside what this audit can check.
That covers the first two bullets under "What was ruled out for the 11", the 2294 rows in
`resolutions` and the 6 tickers in `watchlist`, since no model here reads either table and the
extract does not export them. It also covers every figure drawn from the full fee schedule: the
1659 rows, the 1659 distinct `change_id` and `event_ticker`, the single distinct
`fee_multiplier`, and the 1659 to 1660 row change in the snapshot, because `fixtures/` reduces
`fee_overrides` to 50 rows. The README says as much in both places. Two further limits are
stated in the README and stand: the settlement window is inferred from 263 observations over 6
days, so a feed that occasionally lags beyond 20.2 h would produce false `unexplained` rows that
this extract cannot rule out, and the cause of the 11 is not established here. One CI claim was
checked only by reading: `dbt deps` could not reach `codeload.github.com` from the audit
environment, so `dbt_utils` 1.4.1 was installed from the dbt hub CDN mirror at
`public.cdn.getdbt.com`, with the archive's SHA-1 matching the hash the hub publishes for that
version.
